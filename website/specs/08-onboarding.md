# 08 引導內容規格：世界觀序章、章節開場、每關任務簡報

**一句話重點：玩家在動手前，先知道「這是什麼世界、這關在解決什麼痛、要按哪裡、怎樣算贏」。**

- 起因：玩家回饋看不懂怎麼玩，連熟 K8s 的人第一關都不知道在演什麼，直接關掉
- 根因：現有開場只有劇情 `intro` 與 15 字內的 `gameHint`，缺「痛點 → 概念 → 操作 → 勝利條件」這條線
- 本規格只定內容與呈現方式，不改玩法；每關「怎麼玩」已逐條對照 `src/presentation/games/days/DayNNGame.vue`
- 角色名一律用網站與文章現用名稱（`src/data/characters.ts` 的 `name`）；與 `k8s-series-spec.md` 第 5 節角色表不同處見「3.3 名稱差異」
- 已拍板：第 3.1、4、5 節的角色名已改成網站現用名稱（`src/data/characters.ts` 的 `name`）；3.2、3.3 保留原對照供查

---

## 1. 撰寫規則

**一句話重點：白話、簡短、一屏看完。**

- 每關六個欄位，總字數約 150 字，上限 180 字（不含欄位標題）
- 「怎麼玩」2–4 點，每點一個動作，用畫面上的按鈕原文，以「」標出
- 「K8s 對應概念」的術語沿用 `DayLevel.concept`，後接一句白話定義
- 只寫程式真的會發生的事；計時、命數、失誤上限都照程式常數
- 第二人稱「你」，台灣用語，句尾不加句號

---

## 2. 放置位置

**一句話重點：序章接在「取完暱稱」之後與地圖入口，章節開場放在地圖幕標題與每幕第一關，任務簡報取代關卡開場的任務卡。**

### 2.1 玩家動線

```
① 起始畫面
  ↓
② 序章
  ↓
③ 雲之島地圖
  ↓
④ 關卡簡報
  ↓
⑤ 小遊戲
  ↓
⑥ 過關頁
```

① 起始畫面 `TitleView`：輸入暱稱按開始
② 序章：新的 `/prologue` 頁；只有 `TitleView.start()`（新取暱稱）會導來，`continueGame()` 照舊直接進地圖
③ 地圖 `MapView`：側欄（手機在 HUD 下方）常駐「序章：雲之島是什麼？」入口卡；每幕標題下加一行本章目標
④ 關卡簡報：`DayView` 的 `phase === 'intro'`，簡報卡取代現有「今日任務」卡
⑤ 小遊戲：`phase === 'play'`，標題列多一顆「看簡報」按鈕
⑥ 過關頁：維持現狀

### 2.2 為什麼放這裡

- **序章接在取暱稱之後**：這是每位新玩家必經、且只會經過一次的點；用「從哪個按鈕進來」判斷首次，不需要新存檔欄位
- **地圖放常駐入口**：地圖是所有頁面的樞紐，圖鑑入口卡已在同一位置，玩家找得到；老玩家想重看也有路
- **章節開場掛在既有結構**：`MapView` 已依 `ACTS` 分幕顯示幕名，`DayView` 已顯示 `actOfDay()` 幕名，兩處都只是多一段文字
- **簡報取代任務卡**：`DayView` 每次進關卡都從 `'intro'` 開始（含切換 Day 的 watch），本來就是「先看再開始」，只需換內容，不用加狀態
- **不放在 `GameShell` 的「準備好了嗎？」覆蓋層**：那層寫死在 30 個 Day 元件內，要動 30 個檔；且它只有 360px 寬的卡片，放不下六個欄位

### 2.3 首次進入的判斷

- 不新增存檔欄位
- 序章：靠進入路徑判斷（只從 `start()` 導來）
- 章節開場：靠 `day === act.days[0]` 判斷，每次進該幕第一關都顯示

## 3. 世界觀序章（`/prologue` 顯示內容）

**一句話重點：先講「這座島是 K8s 叢集、角色是元件」，再給三條世界規則，最後告訴玩家 30 天會蓋出什麼。**

### 3.1 序章文字

**雲之島是什麼**

- 雲之島是一座會自己運轉的島，它就是一個 Kubernetes 叢集（Cluster）
- 島上每個角色都對應一個真實的 K8s 元件，比喻只幫你記，正式名稱一定附在旁邊
- 你不用告訴島「怎麼做」，只要說「我想要什麼」，角色們會分工把它變成真的

**三條世界規則**

- ① 小鳥永遠住在泡泡裡：K8s 排程的是 Pod，不是單一 Container
- ② 泡泡會換，柱子不換：Pod 隨時被替換，Service 給你固定入口
- ③ 要留下的資料放地面的倉庫：靠借用單（PVC）接上倉庫（PV），資料才活得過 Pod

**先認識六位核心角色**

- 雲之島（Cluster）：整座島，K8s 管理的範圍
- 巢樹（Node）：島上的樹，一台真的機器或虛擬機
- 泡泡（Pod）：掛在樹上，K8s 部署與排程的最小單位
- 小鳥（Container）：住在泡泡裡，真正跑你程式的容器
- 哨子（kubectl）：你手上的工具，吹出去的指令都送到櫃台
- 燈塔櫃台（API Server）：島的唯一窗口，所有指令與決定都先經過它
- 其他 31 位角色，會在各章開場登場

**這個網站怎麼玩**

- 每天一關，對應一篇文章；先看任務簡報，再玩 1–3 分鐘小遊戲
- 過關後收下「帶走一句話」，角色可到圖鑑猜猜看
- 破完 30 關並在圖鑑答對全部角色，成為「K8s 雲之島統治大王」
- 按鈕：「出發去地圖」

## 4. 章節開場

**一句話重點：每幕一段，講「本章要蓋出什麼」與「會遇到誰」。**

- 顯示位置：`MapView` 幕標題下一行（只放「本章目標」）；`DayView` 每幕第一關的簡報卡上方（放完整一段）
- 「會遇到誰」由 `debutDay` 推導，依登場日排序；同一天依 `characters.ts` 順序，下面列出的是推導結果，供校稿

### 第一幕｜登島（Day 1–5）

- **本章目標**：在筆電上蓋出第一座島，看懂島的結構，學會用哨子下指令
- **蓋完你會有**：一座跑著 Nginx hello 的 Kind 叢集
- **會遇到**：雲之島、巢樹、泡泡、小鳥、燈塔櫃台、選樹官、哨子、管家松鼠、記憶樹、巡邏隊長

### 第二幕｜泡泡與小鳥（Day 6–12）

- **本章目標**：把服務正確包進泡泡，壞了有人補，換版不中斷，起不來會查
- **蓋完你會有**：由 Deployment 管理、能滾動更新與回滾的 hello
- **會遇到**：共享食物桶、食盆、彩色貼紙、放大鏡、貓頭鷹、部署管家

### 第三幕｜流量找得到人（Day 13–18）

- **本章目標**：讓請求不管泡泡怎麼換，都能從島外一路找到小鳥
- **蓋完你會有**：Namespace、Service、Ingress 串好，瀏覽器打得到 hello
- **會遇到**：圍籬、柱子、島內路標、樹幹上的小門、海邊碼頭、地圖看板、守門員、道路管理員

### 第四幕｜帶著東西活下去（Day 19–23）

- **本章目標**：把設定、密碼、資料搬出 image 與泡泡，泡泡換掉也不會忘
- **蓋完你會有**：hello 加 Postgres 的雙層架構，資料活過 Pod
- **會遇到**：便條本、上鎖的小盒子、倉庫、借用單

### 第五幕｜讓島自己運轉（Day 24–28）

- **本章目標**：島自己做健康檢查、分配資源、依流量擴縮，各種工作有專人管
- **蓋完你會有**：會自我修復、自動擴縮的島
- **會遇到**：存活檢查鈴、小旗子、資源需求牌、資源上限線、自動調節旋鈕、編號泡泡管理員、守樹隊長、一次性任務委託單、定時任務鐘

### 第六幕｜收成（Day 29–30）

- **本章目標**：把 30 天的角色串成一張全島運作圖，再值一夜班總複習
- **蓋完你會有**：講得出 K8s 從下指令到資料落地的完整流程
- **會遇到**：全員回場

## 5. 每關任務簡報

**一句話重點：30 關固定六欄；「程式對照」只給實作與驗收看，不顯示。**

### Day 1｜半夜救火員

- **情境痛點**：機器半夜一倒，你得爬起來手動搬服務
- **K8s 對應概念**：Kubernetes：你寫下想要的狀態，它持續幫你維持
- **你的任務**：先手動救火，再把工作交給島
- **怎麼玩**
  - ① 巢樹倒了，點地上的小鳥，再點一棵沒倒、沒滿的巢樹
  - ② 15 秒後按「寫下期望：6 個服務」
  - ③ 換你點巢樹把它推倒，推 2 次
- **過關條件**：推倒 2 棵後，服務回到 6/6
- **玩完你會體會到**：手動救不完；說出結果，島會自己吹新泡泡補上
- 程式對照：`knockManual`（手動階段倒下不長回來）、`placeBird`（不可放倒下或滿 3 隻的樹）、`declare`（所有樹換新機器）、`pushTree`、`PUSHES_TO_WIN = 2`；無失敗狀態

### Day 2｜五分鐘登島

- **情境痛點**：想學 K8s，卻不想先租雲主機、綁信用卡
- **K8s 對應概念**：Cluster：一群機器組成的整體，K8s 管理的範圍
- **你的任務**：在筆電上蓋好島，讓瀏覽器看到 Nginx
- **怎麼玩**
  - ① 照順序點指令卡：蓋島 → 看巢樹 → 跑泡泡 → 看泡泡 → 連進去
  - ② 看終端機輸出，確認每一步成功
  - ③ 有 2 張假卡，點了會被退
- **過關條件**：5 個步驟全部完成
- **玩完你會體會到**：蓋島靠 Kind，之後都靠哨子（kubectl）
- 程式對照：`STEPS` 五步、`DECOY` 兩張、`useSequence`；無失敗狀態

### Day 3｜島嶼點點名

- **情境痛點**：Cluster、Node、Pod 在腦中糊成一團
- **K8s 對應概念**：Cluster／Node／Pod：叢集包節點，節點跑 Pod，Pod 裝容器
- **你的任務**：分清楚每題問的是哪一層
- **怎麼玩**
  - ① 讀題目，可能是指令或一句描述
  - ② 點下方「島／樹／泡泡／小鳥」作答，答錯會亮出正解，重答即可
  - ③ 答完後點一顆泡泡，看誰受影響
- **過關條件**：答完 8 題，並戳破一顆泡泡
- **玩完你會體會到**：泡泡破了重吹，雲之島和巢樹都不動
- 程式對照：`QUESTIONS` 8 題、`answer`、`step = 'egg'`、`popPod`；無失敗狀態

### Day 4｜燈塔村接力

- **情境痛點**：看到一堆沒建過的系統泡泡，不知道誰在管島
- **K8s 對應概念**：Control Plane：負責記錄、決策、調整的核心元件群
- **你的任務**：把「我要 3 顆泡泡」一棒棒傳到巢樹上
- **怎麼玩**
  - ① 看任務卡的提問，找出下一棒
  - ② 依序點角色接力，每一棒都要經過燈塔櫃台
  - ③ 第 2 輪泡泡破一顆，從巡邏隊長開始補
- **過關條件**：兩輪都由管家松鼠吹出泡泡
- **玩完你會體會到**：你只說結果，巡邏隊長負責把現實調成你要的
- 程式對照：`ROUNDS` 兩輪、`TO_PICKER`、記憶樹為干擾（點了提示「只跟櫃台說話」）；無失敗狀態

### Day 5｜哨子點唱機

- **情境痛點**：kubectl 指令上百個，不知道日常該用哪幾個
- **K8s 對應概念**：kubectl：對燈塔櫃台下指令的命令列工具
- **你的任務**：依任務單組出正確的指令
- **怎麼玩**
  - ① 讀任務單，對象已經幫你填好
  - ② 點一個動詞；選 get 時可再加 -n dev、-A 或 -o yaml
  - ③ 按「吹！」送出
- **過關條件**：75 秒內完成 8 張任務單，時間到會加送 20 秒一次
- **玩完你會體會到**：排查時先看狀態、再看事件、最後看日誌
- 程式對照：`TOTAL_SEC = 75`、`BONUS_SEC = 20`、`ROUNDS = 8`、`pickVerb`、`pickFlag`、`blow`（動詞錯就清掉，預覽不拼出假指令）；第二次時間到判失敗

### Day 6｜泡泡室友配對

- **情境痛點**：Docker 直接跑容器就好，為何要多包一層 Pod
- **K8s 對應概念**：Pod：最小部署單位，容器共用網路；要共享檔案得掛同一個 Volume
- **你的任務**：判斷兩隻小鳥該同住一顆泡泡，還是分開住
- **怎麼玩**
  - ① 點一隻小鳥，再點泡泡 A 或 B 放進去
  - ② 兩隻都放好，按「吹泡泡」
  - ③ 放錯會說明原因，重放即可
- **過關條件**：4 回合都配對正確
- **玩完你會體會到**：要一起生、一起死的才住同一顆，這就是 sidecar
- 程式對照：`ROUNDS` 4 回合、`pickBird`、`tapBubble`、`blow`；無失敗狀態

### Day 7｜YAML 縮排師

- **情境痛點**：kubectl run 無法交給同事、放進 git
- **K8s 對應概念**：Pod YAML：用 apiVersion、kind、metadata、spec 描述 Pod
- **你的任務**：修好這份 YAML，讓燈塔櫃台收件
- **怎麼玩**
  - ① 點左邊的「n 格」切換縮排，一層縮 2 格
  - ② 點藍色的值改 apiVersion、kind
  - ③ 按「送去櫃台」，照退件訊息修
  - ④ 收件後點泡泡刪掉
- **過關條件**：櫃台收件，刪掉後沒人補回
- **玩完你會體會到**：縮排代表從屬；單獨的 Pod 刪了不會回來
- 程式對照：`cycleIndent`、`toggleValue`、`send`、`validate`、`deletePod`；無失敗狀態

### Day 8｜放大鏡尋寶

  - ③ 五條接完，回答兩題燈塔村停電題
- **過關條件**：五條線接通，停電題都答對
- **玩完你會體會到**：決定和執行分開，燈塔村停電，巢樹上照樣跑
- 程式對照：`LINES` 五條、`tap`、`QUESTIONS` 2 題；接通後名稱鏈寫在任務卡（`lastChain`），提示氣泡只留短句；無失敗狀態

### Day 30｜雲之島值班夜

- **情境痛點**：學了 30 天，真的出事還是不知道先做什麼
- **K8s 對應概念**：Reconciliation：控制器持續把現況拉向你宣告的期望狀態
- **你的任務**：連續處理 5 個島嶼事故
- **怎麼玩**
  - ① 讀事故描述
  - ② 20 秒內選處置，時間到會加送 10 秒一次
  - ③ 看正解與理由，按「下一題」
- **過關條件**：5 題答完，3 條命沒用完
- **玩完你會體會到**：你不再記哪台跑什麼，島替你記
- 程式對照：`QUESTION_SEC = 20`、`EXTRA_SEC = 10`、`LIVES = 3`、`choose`、`next`

## 6. 呈現與互動

**一句話重點：每次進關卡先看簡報，按「開始」才進遊戲，遊戲中隨時可重開簡報。**

### 6.1 關卡開場（`DayView` `phase === 'intro'`）

- 手機版由上而下：幕名 → 標題 → 章節開場（僅每幕第一關）→ 簡報卡 → 開始按鈕 → 劇情、主圖、登場角色
- 簡報卡六欄依序：情境痛點、K8s 對應概念、你的任務、怎麼玩、過關條件、玩完你會體會到
- 開始按鈕沿用 `data-test="start-game"`，文字沿用「開始任務／再玩一次」
- 劇情、主圖、登場角色移到按鈕下方，往下滑才看到
  - 取捨：主圖是氛圍入口，往下移會少一點故事感；換來的是 360px 首屏就看到「要做什麼」
- 桌機（≥ 1024px）：左欄放主圖、劇情、登場角色，右欄放幕名、標題、章節開場、簡報卡；兩欄靠上對齊，左欄捲動時黏在頂部
- 開始按鈕在簡報卡內 `position: sticky` 貼底，簡報比第一屏長時仍看得到
  - 驗收：1280×800 全部 30 關、360×740 全部 30 關，`start-game` 都在第一屏內
  - `tests/e2e/onboarding.spec.ts` 逐關檢查 1280×800
- 登場角色直接顯示名稱，與章節開場「會遇到」一致（見 8.3 採選項 A）

### 6.2 遊戲中重看（`phase === 'play'`）

- `play__head` 加一顆「看簡報」按鈕，點開彈窗顯示同一張簡報卡，關閉回到遊戲
- 不卸載遊戲元件，進度不丟
- 彈窗開著時遊戲暫停：計時、倒數、節拍與延遲事件都停住，關閉後接著跑
  - 做法：`DayView` 以 `provide(GAME_PAUSED, briefingOpen)` 提供暫停訊號，kit 的 `useCountdown`、`useTicker`、`useTimeouts` 讀取
  - 有計時或倒數的關卡（Day 1、5、9、14、16、21、24、30）彈窗內加一行小字「看簡報時遊戲暫停，回到遊戲後繼續」
- 關閉方式：「回到遊戲」按鈕、點遮罩、按 Esc

### 6.3 與 `GameShell` 覆蓋層的關係

- 保留「準備好了嗎？」覆蓋層，不改 30 個 Day 元件
- 進遊戲仍是兩次點擊：簡報「開始任務」→ 覆蓋層「開始 ▶」
- 取捨：多一次點擊；好處是計時從玩家看見舞台後才開始

### 6.4 章節開場

- `MapView`：每個 `act__name` 下加一行「本章目標」
- `DayView`：`day === act.days[0]` 時，在簡報卡上方顯示本章目標、蓋完你會有、會遇到

### 6.5 序章

- 新增 `/prologue` 路由，內容見第 3 節
- `TitleView.start()` 改導向 `/prologue`；`continueGame()` 維持導向 `/map`

## 7. 資料型別草案

**一句話重點：簡報掛在既有 `DayLevel` 上，章節只多一個目標欄位，序章是靜態頁面文字。**

```ts
// src/domain/level.ts
export interface DayBriefing {
  /** 情境痛點，1 句 */
  pain: string
  /** 概念白話定義，1 句；術語沿用 DayLevel.concept */
  conceptPlain: string
  /** 你的任務，1 句 */
  goal: string
  /** 怎麼玩，2–4 點 */
  steps: string[]
  /** 過關條件 */
  winCondition: string
  /** 玩完你會體會到，1 句 */
  insight: string
}

export interface DayLevel {
  // …既有欄位不變
  briefing: DayBriefing
}

export interface Act {
  id: number
  name: string
  days: [number, number]
  /** 本章目標 */
  goal: string
  /** 蓋完你會有 */
  result: string
}
```

- 不放 `day`：掛在 `DayLevel` 底下，天數已由外層決定
- 不放術語欄位：直接用 `DayLevel.concept`，避免兩處不同步
- 不放章節角色清單：用 `CHARACTERS` 的 `debutDay` 落在 `Act.days` 區間推導
- 不放序章型別：序章只有一頁，文字寫在 `PrologueView.vue`
- 建議驗證（`tests/unit/data/content.test.ts`）
  - 30 關都有 `briefing`，`steps` 長度 2–4
  - 六欄總字數 ≤ 180
  - 每個 `Act` 的 `goal`、`result` 非空

## 9. 需求外建議

**一句話重點：以下都不是必做，預設不加，勾選才做。**

- ~~**開簡報時暫停計時**~~：已採用，見 6.2
- **已過關的關卡預設收合簡報**
  - 為什麼：老玩家重玩不必每次看六欄
  - 做法：用既有 `clearedDays` 判斷，不新增存檔欄位
  - 不加的風險：重玩多滑一下，影響小
  - 成本差異：之後加只動 `DayView`，現在加沒有省成本
- **統一提示文字來源**
  - 為什麼：`gameHint` 與 `GameShell hint` 曾經不同步（見 8.2）
  - 做法：Day 元件改讀 `LEVELS` 的 `gameHint`
  - 不加的風險：之後改提示要改兩處；目前已有單元測試逐關比對，漂移會被擋下
  - 成本差異：要動 30 個 Day 元件；越晚做越多處要比對
- **不建議**：新增「已看過序章」「已看過簡報」存檔欄位；首次判斷已可由進入路徑與既有進度推導
